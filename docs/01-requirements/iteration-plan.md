# 迭代规划

## 1. 迭代原则

项目采用四周、每周一个 Sprint 的敏捷开发节奏。每个 Sprint 结束必须提交可运行的软件增量、更新后的文档和清晰的 Git 记录。

| Sprint | 周期 | 核心目标 | 可运行增量 |
| --- | --- | --- | --- |
| Sprint 1 | 第 1 周 | 需求、建模、项目骨架、身份认证 | 可登录，可查看空行程列表 |
| Sprint 2 | 第 2 周 | 模拟行程、碳核算、积分账本 | 上报行程后获得积分，可查流水 |
| Sprint 3 | 第 3 周 | 商品、兑换、库存和运营管理 | 完成“浏览商品→兑换→查订单”闭环 |
| Sprint 4 | 第 4 周 | 测试、部署、报告和演示 | 可部署版本、完整测试记录和实验报告 |

## 2. 小组分工

以下为建议分工，姓名由组长确定后补充。

| 角色 | 姓名 | 主要职责 |
| --- | --- | --- |
| 组长/产品与需求 | 待填写 | 需求冻结、进度协调、用例与报告统筹 |
| 后端与领域逻辑 | 待填写 | 接口、碳核算、积分账本和事务一致性 |
| 前端与交互 | 待填写 | 用户端、管理端页面和前后端联调 |
| 测试与数据/部署 | 待填写 | 数据库、测试用例、自动化测试和部署 |

每名成员都必须有可追踪的代码、文档、测试或评审贡献，不能只以会议参与作为贡献依据。

## 4. 各 Sprint 验收

### Sprint 1

- 完成实验一全部需求和 UML 分析模型。
- 初始化前后端项目、数据库、统一错误格式和基础 CI 检查。
- 完成注册、登录、角色鉴权和空行程列表。
- 建立 Git 分支、Issue/任务和 Pull Request 流程。

### Sprint 2

- 支持四类模拟行程上报和查询。
- 碳核算规则可配置、可版本化，历史计算使用快照。
- 同一行程只能发放一次积分。
- 积分余额和积分流水保持一致。

### Sprint 3

- 完成商品浏览、商品详情和兑换。
- 余额、库存、订单和积分流水在同一事务中更新。
- 完成管理员规则、商品、库存和订单页面。
- 完成基本运营统计。

### Sprint 4

- 完成单元测试、集成测试和关键并发测试。
- 完成部署说明和可重复部署验证。
- 完成实验报告、测试记录、AI 使用记录和组内互评。
- 准备可演示的端到端流程和异常场景。

## 5. 完成定义

一个用户故事只有同时满足以下条件才算完成：

1. 代码已实现并通过自测。
2. 关键业务规则有自动化测试。
3. 接口和数据库变更已同步到设计文档。
4. 通过至少一名其他成员的代码评审。
5. 有清晰的 Git 提交记录。
6. 所属 Sprint 的可运行增量能够演示。

## 6. Git 协作约定

- `main` 保持可运行，不直接提交未评审的功能。
- 每个用户故事使用独立功能分支，例如 `feature/US-04-trip-report`。
- 提交信息说明模块和目的，例如 `feat(trip): add simulated trip reporting`。
- 合并前至少经过一次评审；冲突由当时代码负责人解决。
- 每个 Sprint 结束时打 Tag，例如 `sprint-1`。
- 实验报告记录 AI 使用范围、人工修改和验证过程。

## 7. 主要风险与控制

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 范围膨胀 | 核心闭环无法完成 | 严格冻结 MVP，地图、支付、区块链不进入当前迭代 |
| 碳因子缺乏依据 | 结果不可解释 | 规则配置化，文档标注模拟假设和规则版本 |
| 积分与库存并发错误 | 数据不一致 | 唯一约束、幂等键、事务和并发测试 |
| 过度微服务化 | 联调成本过高 | 采用模块化单体，保留领域事件和清晰模块边界 |
| 末期集中提交 | Git 贡献不可信 | 每个故事完成后立即提交与评审 |
